## (A) 外部依存なしで図を描く方法

### 1. 選択肢比較

| 方式 | 追加依存 | 生成物サイズ | 日本語フォント | テストのしやすさ |
|---|---|---|---|---|
| **自前で SVG 文字列を組む**（Python 関数 + f-string、または Jinja2 マクロ） | **なし**（標準ライブラリのみ。エスケープは `xml.sax.saxutils.escape` かテンプレートの `autoescape`） | 最小。手で書いた分しか出ない（実測は §5） | `<text>` に `font-family` を書くだけ。システムにある日本語フォント名を並べれば良く、埋め込み不要 | 高い。文字列アサーション／XML パースで座標や値を直接検証できる。ゴールデンファイル比較も容易 |
| **pygal**（純Python、SVGテンプレート方式） | 中。`pygal` 本体は軽いが `cairosvg`（PNG変換用、任意）や `lxml`（テンプレート）に依存する構成もあり、バージョンによって挙動が変わる。今回は未インストールでの追加導入が必要 | 中〜大。デフォルトでCSS埋め込み・グリッド・凡例・インタラクション用の `<script>` 相当のスタイルまで生成され、素朴な棒グラフでも数KB〜10数KBになりやすい（要出典確認、実測はしていない） | フォント指定はCSS経由で可能だが、pygal自身のデフォルトCSSと衝突しないよう上書きが必要 | 中。ライブラリの出力フォーマットに依存するため、「値→座標」の単体テストがしづらく、出力XMLのスナップショット比較に寄りがちになる |
| **svgwrite** | 小〜中。ライブラリ自体は薄いビルダー（要素をPythonオブジェクトで組み立ててシリアライズするだけ）だが、それでも「自前で文字列を組む」より依存が1つ増える | 自前実装とほぼ同等（薄いラッパーなので余計な装飾は付かない） | 自前実装と同様、`style` 属性やCSSクラスで自由に指定できる | 自前実装と同程度に高い（要素オブジェクトの属性を検証できる） |
| **matplotlib の SVG 出力** | **重い**。`matplotlib` は `numpy`（既存依存）に加え `pillow`・`fonttools`・`kiwisolver`・`pyparsing`・`contourpy`・`cycler` 等を新規に引き込む。インストールサイズは数十MB規模になり、「重い依存を増やしたくない」という制約に明確に反する | 大きい。デフォルトでは `<defs>` にフォント埋め込み用パスデータや `clip-path` が多数生成され、単純な折れ線でも自前実装の何倍にもなりやすい（`svg.fonttype: 'none'` にすればテキストは軽くなるが、それでも装飾要素が多い） | `rcParams['font.family']` にシステム日本語フォント名を指定すれば描画自体は可能。ただし `svg.fonttype` の設定次第でテキストがパス化され、さらにサイズが増える | 低〜中。図の生成はテスト容易だが「出力SVGの中身」を検証するテストは書きにくく、通常は「例外が出ないこと」程度の保証に留まりがち。バックエンド初期化やフォントキャッシュ構築でテスト起動が重くなる |
| **plotly の static 出力** | **最重量**。SVG/PNG静止画エクスポートには `kaleido`（Chromiumベースのヘッドレスレンダラ）が必要で、数百MB規模。ローカルGUIアプリの追加依存としては明確に過剰 | 大きい。plotly自体がインタラクティブ用途のため、静的出力でも冗長なマークアップになりやすい | Chromiumのレンダリングに依存するため管理外の要素が増える | 低。外部プロセス（kaleido）を介するため単体テストが遅く不安定になりやすい |

**結論（推奨）**: **自前で SVG 文字列を組む**（Python のヘルパー関数、必要なら Jinja2 マクロで薄くラップ）。
理由:
- 唯一「追加依存ゼロ」で完結する（CLAUDE.md/SPEC の「重い依存を増やしたくない」という要件に最も適合）
- 生成物が最小（§5 の実測で1図あたり数百バイト〜2.5KB程度）
- 既存の `templates/report.html.j2` は Jinja2 + `autoescape=True` の構成なので、SVG生成も「文字列を作って `| safe` なしでテンプレートに渡す」か、`app/ai/report.py` 側でSVG文字列を組み立てて `AnalysisReport` から独立したコンテキスト値として渡す形に自然に統合できる
- テストが素直（値→座標の変換式を関数として切り出せば、`pytest` で `x_of(i)`・`y_of(v)` のような座標計算だけを単体テストでき、出力SVGの文字列中に期待する `<rect>`/`<polyline>` の断片が含まれるかを assert する形も書きやすい）

ただし **AI 出力を埋め込むのはSVGではなく地の文（`summary`等）のみ**という前提を维持し、SVGを組み立てる際の数値・ラベルも `esc()`（`xml.sax.saxutils.escape` 相当、または Jinja2 の autoescape 経由）を必ず通すこと。テンプレートに直接 `<text>{{ label }}</text>` のように埋め込むなら Jinja2 の autoescape がそのままXSS対策になるので、**SVG生成をテンプレート内マクロで行うのが最も安全**（Python側で文字列結合して `Markup()`/`|safe` にすると autoescape の恩恵が切れるので注意）。

### 2. よく使う図のインラインSVG実装パターン（座標変換・軸・目盛りの定石）

共通の考え方は「データ空間 → 画面空間の線形写像を1関数にする」こと。実装したパターン（`scratchpad/svgtest/gen_svg.py`）:

- **スパークライン**（`sparkline()`）: 軸なし。`x = i/(n-1)*width`、`y = height - (v-lo)/(hi-lo)*height` の2行だけ。最後の点に強調用の `<circle>` を1つ置くのが定石（直近値を示す）
- **折れ線**（`line_chart()`）: `pad_l/pad_r/pad_t/pad_b` の余白を確保し、プロット領域幅・高さを `width/height - padding` で決める。Y軸目盛りは等間隔4〜5本を `<line>`（グリッド）＋`<text>` で描画。X軸ラベルは全日付を出さず、**先頭・中央・末尾の3点だけ**に間引くのが実装コストと可読性のバランスが良い定石（実測で60日分でも十分読める）
- **棒グラフ**（`bar_chart()`）: ゼロ基準線 `zero_y = y_of(0)` を先に決め、各バーは `y = min(y_of(v), zero_y)`、`height = abs(y_of(v) - zero_y)` で負値にも対応できる形にしておくと、後で赤字（営業損失など）が出ても式を変えずに済む
- **棒＋折れ線の複合**（`combo_bar_line()`）: 2系列は値域が違うことが普通なので、**軸を系列ごとに正規化**（棒は0〜最大値、折れ線は最小〜最大）してから同じピクセル空間に描く。色分け（例: 棒=`--accent`、線=`--bull`）と凡例相当のテキストで見分けをつける。SVGネイティブの「第2Y軸」という概念は無いので、目盛りラベルをどちらか一方（または両方を左右に）出す設計にする
- **横棒（レンジ内位置）**（`range_bar()`）: 背景に太い角丸 `<rect>`（レール）、現在値位置に `<circle>`（つまみ）。`aria-label` に「安値〜高値のうち現在値」を文章で埋め込むと、視覚要素なしでも意味が伝わる（アクセシビリティ対応にもなる）

いずれも **丸め処理**（`f"{x:.1f}"`）を入れることで座標の桁数を抑え、ファイルサイズと可読性の両方を改善できる（小数第1位で視覚的には十分）。

### 3. SVGの作法

- **`viewBox` + `width="100%" height="auto"`**: `viewBox="0 0 640 220"` を固定し、`width="100%"`（`height` は `auto` または明示せず `viewBox` のアスペクト比に委ねる）にすると、レポートの `max-width: 900px` のようなレイアウトに素直に追従する。レスポンシブにしたい場合はこれで十分で、JS計算は不要
- **`preserveAspectRatio="xMidYMid meet"`**: デフォルト値と同じだが明示しておくと意図が読める。中央寄せ＋アスペクト比維持で崩れない
- **フォント指定**: 外部フォントは使えない（オフライン・単一HTML）ので、`<style>` 内 `font-family` に **既存の `report.html.j2` と同じシステムフォントの並び**（`"Hiragino Kaku Gothic ProN","Yu Gothic","Meiryo",sans-serif`）を使う。Windowsのターゲット環境なら `Yu Gothic`/`Meiryo` で確実に和文が出る。SVG内の `<text>` に直接 `font-family` 属性を書いてもよいが、複数の `<text>` がある場合は `<style>` 内でクラス指定した方がサイズが増えにくい（実測で確認、§5）
- **アクセシビリティ**: `role="img"`（SVGはデフォルトでは読み上げ順序が不定なため明示）、`<title>`（先頭の子要素、簡潔な図の説明）、必要なら `<desc>`（詳細説明、値の要約など）。さらに `aria-label` を `<svg>` 自体にも付けておくと、`<title>` の読み上げに対応しないスクリーンリーダーでも情報が伝わる（両方付けるのが実務上の保険）。実装した5パターンはすべて `role="img"` + `aria-label` + `<title>` を付けてある

### 4. 印刷

- インラインSVGは基本的に**ラスタ画像より印刷に強い**（ベクタなので拡大縮小で滲まない）。ブラウザ・WebView2の印刷パイプラインはSVGを素直にサポートしている
- `@media print` で必要になりやすいのは主に次の2点:
  - **ページ内改行の抑制**: `.chart { break-inside: avoid; }`（または `page-break-inside: avoid;` の併記。古いレンダラ互換のため両方書くのが無難）。図の途中でページが割れるのを防ぐ
  - **色の出力方針**: 既定では背景色付きの `<rect>` 等はブラウザ側の「背景のグラフィックを印刷」設定に依存し、無効だと消えることがある。**線・文字は前景色として描く**（`fill`/`stroke` に濃い色を使い、背景を塗りつぶしに頼らない）設計にしておけば、白黒印刷でも情報が消えにくい
- CSS変数（`var(--accent,#274690)`）をそのまま `fill`/`stroke` に使っている場合、`@media print` 側で変数を上書きすれば印刷時だけ配色を変える（例: 淡い色を濃色に）ことも可能。今回のサンプルSVGはCSS変数にフォールバック値を持たせているので、変数未定義環境（単体のSVGファイルとして開かれた場合など）でも見た目が破綻しない
- 崩れの主な原因になりやすいのは「固定px指定の親コンテナ」の方で、SVG側は `viewBox` を使っていれば通常問題ない。**実機（Edge WebView2）での印刷プレビュー確認は必須**（§7 未解決事項）

### 5. サイズの目安（実測）

`scratchpad/svgtest/gen_svg.py` で実際に生成し、UTF-8バイト数と gzip -9 後のバイト数を測定した（乱数シード固定、日本語ラベル・凡例込み）。

| 図 | 説明 | 生バイト数 | gzip -9 |
|---|---|---|---|
| スパークライン | 直近20日、軸なし | **556 B** | 396 B |
| 折れ線 | 60日終値、Y軸目盛り5本＋X軸ラベル3点 | **2,425 B** | 986 B |
| 棒グラフ | 5期分、値ラベル・軸ラベル付き | **1,745 B** | 626 B |

### 6. ダークモード

- SVG内の色を `fill="var(--accent,#274690)"` のように **CSS変数＋フォールバック値** で指定し、埋め込み先のHTML `<style>` 側で
  ```css
  :root { --accent:#274690; --fg:#1a1a1a; --muted:#5b6472; --border:#d8dce3; --grid:#e3e6ec; }
  @media (prefers-color-scheme: dark) {
    :root { --fg:#e8eaed; --muted:#9aa4b2; --border:#333a45; --grid:#2a2f38; }
    body { background:#14161c; }
  }
  ```
  のように上書きすれば、SVGの `fill`/`stroke` もページ全体のテーマに自動追従する。**SVGは `<img>` タグで埋め込まず、HTML内にインライン展開する**ことが前提条件（`<img src="data:image/svg+xml,...">` にすると、そのSVGは別ドキュメント扱いになり親ページのCSS変数を継承できないため、ダークモード追従が効かなくなる）
- 印刷との両立: `@media print` は多くの場合 `prefers-color-scheme` の値に関わらず「印刷用の配色」を別途強制すべき（上記の白黒印刷の項を参照）。`@media print { :root { --fg:#000; --muted:#333; ... } }` のように印刷時だけ変数を上書きすれば、画面がダークモードでも印刷は黒基調になり読みやすい
- 現状の `templates/report.html.j2` は固定の `:root` 変数を持つのみでダークモード対応が無い（`background:#fff` 固定）。SVGだけダークモード対応してもページ本体が白背景のままではチカチカするので、**SVG側の対応とレポートHTML本体側の `prefers-color-scheme` 対応はセットで検討すべき**（本タスクの範囲外だが、実装時に合わせて手当てが必要な点として申し送り）

## (B) アプリ内で HTML レポートを表示する方法

### 0. 前提として判明した重要な制約

上記「現状把握」の通り、**`data/reports/*.html` は pywebview の内蔵サーバーからも `dev_server.py` からも配信されない**（配信ルートが `web/` ディレクトリに固定されているため）。
したがって、`<iframe src="../data/reports/xxx.html">` のような **相対パスでの直接参照は本番・開発のどちらでも成立しない**。選択肢は実質的に次の2つに絞られる。

1. Python側（`app/api.py`）に新しいメソッド（例: `get_report_html(report_id)`）を追加し、**HTMLの中身を文字列としてJS側に返す**→ `iframe.srcdoc` または `Blob` に流し込む
2. `file://` URLを直接使う（`path.as_uri()` を `iframe.src` に指定）

### 1. iframeにHTML文字列を流し込む方法の比較

| 方法 | Edge WebView2（pywebview）で動くか | dev_server（ブラウザ）で動くか | サイズ制限 | 同一オリジンポリシー | `sandbox` との相性 |
|---|---|---|---|---|---|
| **`iframe.srcdoc = html`** | 動く。WebView2はChromiumベースでモダンHTML仕様に準拠しており `srcdoc` は標準サポート範囲 | 動く（通常のChromium系ブラウザと同じ） | 明文化された仕様上の上限は無いが、実務上は「巨大な文字列をDOM属性に流し込む」形になるため、数百KB〜数MBを超えると描画がもたつく可能性がある（本レポートの用途＝数KB〜数十KB程度なら全く問題にならない） | `srcdoc` で読み込まれた文書は `about:srcdoc` として**埋め込み元と同一オリジン扱い**になる（`sandbox`未指定時）。これは「AIの出力を埋め込んだ文書が親ページのDOM・Cookie等にアクセスできてしまう」ことを意味するため、**`sandbox` 属性の併用が実質必須**| 相性良い。`sandbox="allow-..."` を明示すればオリジンを分離できる（後述） |
| **`Blob` + `URL.createObjectURL`** | 動く。`URL.createObjectURL(new Blob([html], {type:"text/html"}))` を `iframe.src` に設定する方式 | 動く | `srcdoc` よりは大きなペイロードでも扱いやすいとされる（メモリ上のオブジェクトなのでDOM属性の文字列化コストが無い）が、今回の用途では差は誤差の範囲 | Blob URLは生成元のページと**別オリジン**（`null` origin）として扱われる。`sandbox` を付けなくても親ページと直接のDOM共有はできない分、`srcdoc`よりは事故りにくいが、`postMessage`等での連携がしたい場合はオリジンの扱いに注意が必要 | 相性良い。`URL.revokeObjectURL()` で明示的に解放する後始末が必要（メモリリーク防止） |
| **`iframe.contentDocument.write()`** | 動くが**非推奨API**（`document.write` はモダンブラウザで警告が出ることがあり、`sandbox` に `allow-same-origin` が無いと `contentDocument` へのアクセス自体が例外になる） | 同様に動くが非推奨 | 制限は特にないが実装として古い | `contentDocument` にアクセスするには `allow-same-origin` が前提になりやすく、AI生成物の隔離という目的と矛盾しやすい | 相性が悪い（`sandbox`との併用が難しい） |
| **`file://` を直接読ませる** | pywebview の場合、メイン画面自体が `web/index.html` を（内蔵サーバー経由の `http://` または `file://`、モードによる）で読み込んでいる。仮にメイン画面が `http://` オリジンだとすると、そこに埋め込む `<iframe src="file:///...">` は**クロスオリジン扱い**になり、WebView2のセキュリティモデル上こちらからのDOM相互作用（高さ取得など）が制限される可能性が高い。加えて `data/reports` は現状どのオリジンにも公開されていないディレクトリなので、そもそも `file://` パスを直書きするのは「隠しディレクトリ構造への依存」を増やすだけで筋が良くない | dev_server利用時（ブラウザで `http://127.0.0.1:8765/...` を開いている場合）は尚更、`file://` iframeはブラウザの混在コンテンツ制限に引っかかりやすい | 該当ファイルサイズに制限なし（ディスクから読むだけ） | 最悪。`http(s)` ページに埋め込んだ `file://` iframeはブラウザによって全面ブロックされることもある | 相性が悪い（`sandbox`の効果自体が怪しくなる組み合わせ） |

**推奨（B-1）**: **`get_report_html(report_id)` をAPIに追加して文字列として取得し、`iframe.srcdoc` に設定 + `sandbox` 属性で隔離**。理由:
- 既存の `app/api.py` の設計（JSON往復でPythonの戻り値をJSに渡す）にそのまま乗る。`ai_report.get_report()` は既にパスを返しているので、`path.read_text(encoding="utf-8")` を足すだけで実装できる
- レポートは「単一HTML・外部参照なし」という制約により生成されているため、`srcdoc` に丸ごと渡しても表示が壊れない（外部CSS/JS/画像を読みに行く必要が無い）
- サイズは (A) の実測（1件あたり数KB〜数十KB程度）を踏まえると `srcdoc` のオーバーヘッドは無視できる。将来的にレポートが数MB級に肥大した場合は `Blob` 方式へ切り替える余地を残しておく

### 2. `sandbox` 属性の適切な設定

AI生成物（`summary`等）をそのまま埋め込んだHTMLを表示する前提なので、**最小権限**が原則。

```html
<iframe sandbox="allow-popups allow-modals" srcdoc="..."></iframe>
```

- **`allow-scripts` は付けない**: レポートHTMLは静的なマークアップ（Jinja2 `autoescape=True` でAI出力を埋め込んだテキストとSVG）であり、スクリプト実行を許す理由がない。仮にエスケープ漏れがあった場合の**最後の防波堤**として `allow-scripts` を外しておく意義が大きい
- **`allow-same-origin` は付けない**: これを付けると、`srcdoc` の文書が親ページと同一オリジン扱いになり、`allow-scripts` と組み合わさった場合に親のDOM・`window.pywebview.api` 等へアクセスできる可能性が生まれる（この組み合わせは一般に安全性が大きく損なわれるパターンとして知られている）。**スクリプトを禁じるなら `allow-same-origin` の有無は実害が小さいが、「両方とも禁じる」を既定にしておくのが安全側**
- 印刷を `iframe.contentWindow.print()` でトリガーしたい場合、`allow-modals` が無いと `print()` のダイアログ表示がブロックされる可能性がある（ブラウザ実装依存）ので、印刷機能を提供するなら `allow-modals` を許可リストに入れる
- リンク遷移（レポート内に外部リンクは無い想定だが、念のため）は既定でブロックされる（`allow-top-navigation`等を付けない限り）。**AI生成テキストにMarkdown由来のリンクが混入する可能性を考えると、リンク系の許可は一切与えない方が安全**
- まとめると推奨値: **`sandbox="allow-modals"`**（印刷を提供する場合）または **`sandbox=""`**（印刷は別ボタンから「OS既定ブラウザで開く」に逃がす場合。既存の `open_report` 導線を残せば代替手段になる）

### 3. iframeの高さの扱い

- **固定高さ＋内部スクロール**が最も簡単で、`sandbox` の設定に関わらず確実に動く: `iframe { width:100%; height: calc(100vh - ヘッダー分); border:0; }` とし、レポート本文側のスクロールに任せる。**推奨はこちら**（後述の理由）
- **中身の高さに合わせて伸ばす**方法は主に2通り:
  - `iframe.contentWindow.document.documentElement.scrollHeight` を読んで `iframe.style.height` に反映。ただしこれは `sandbox` に **`allow-same-origin` が無いと `contentWindow.document` へのアクセスが例外になる**（クロスオリジン扱いのため）。つまり「高さ自動追従」と「`allow-same-origin` を外した安全な隔離」は**両立しない**
  - 妥協策として、`postMessage` でiframe内から高さを親に送る方式があるが、これには **iframe内にスクリプト（`allow-scripts`）が必要**になり、「AI生成物にスクリプトを実行させない」という方針と衝突する
- **結論**: 今回の用途（AI生成HTMLを安全に隔離して表示）では、**`allow-same-origin` を外したまま高さ自動追従を実現する簡単な方法は無い**。素直に「固定高さ＋内部スクロール」を採用し、iframe自体は画面の残り高さいっぱいに広げるのが安全性とのトレードオフとして妥当

### 4. pywebviewで別ウィンドウ表示する手段

**ある。** `webview.create_window(title, html=html_string, ...)` を **`webview.start()` 実行中に呼び出す**ことで、実行時に新しいネイティブウィンドウを追加できる（`.venv/Lib/site-packages/webview/__init__.py` の `create_window` シグネチャで `html: str | None` を直接受け付けることをソースで確認済み）。
- `main.py` の `Api` クラスに `open_report_window(report_id)` のようなメソッドを足し、その中で `webview.create_window(f"レポート {symbol}", html=html_text, width=900, height=1000)` を呼べば、**iframeもsandboxも介さずに独立したネイティブウィンドウとしてレポートを開ける**。この場合、ウィンドウの中身は通常のトップレベル文書としてロードされるため、`window.print()` や `scrollHeight` の取得にも制限がかからない（＝(B)-3の高さ問題や印刷の制約を回避できる）
- 一方で「タブの中で見せたい」という当初の要望（一覧とプレビューを行き来する軽快さ）には合わないため、**「アプリ内タブでのプレビュー」と「別ウィンドウで開く」を両方用意し、ユーザーに選ばせる**（既存の「開く」ボタンをこの別ウィンドウ方式に置き換え、`webbrowser.open`によるOSブラウザ起動は「外部ブラウザで開く」として残す）設計が現実的
- 新規ウィンドウの `html=` はロード後に差し替えできない前提の使い方が単純（`window.load_html()` で後から差し替えることも可能）。用途としては「レポート1件ごとに新規ウィンドウを開く」で十分

### 5. 印刷・保存の導線

- `iframe.contentWindow.print()` は、**`sandbox` に `allow-modals` が無いと動かない可能性が高い**（印刷ダイアログはモーダルUIの一種として扱われる実装が一般的）。`allow-scripts` も同時に必要になる点に注意（`contentWindow.print()` を親から呼ぶ場合は親のスクリプトなので `allow-scripts` は不要なはずだが、Chromiumの実装によっては挙動確認が要る＝**実機確認が必要な点**として申し送り）
- **確実に印刷したいなら**、(B)-4の「別ウィンドウで開く」方式（sandboxなしの独立ウィンドウ）か、既存の「OS既定ブラウザで開く」（`webbrowser.open`、これは無条件に印刷可能）を印刷用の主導線として案内するのが安全側。iframe内プレビューはあくまで「内容の確認」用途に限定し、印刷ボタンは別に「外部ブラウザで開く」を用意する、という役割分担が実装コストと安全性のバランスが良い
- 保存については、レポートは既に `data/reports/` にファイルとして存在するので「保存」操作自体は不要（既存の `open_reports_folder` でエクスプローラーからコピー等が可能）。強いて言えば「このタブから直接`名前を付けて保存`」は `sandbox` 環境のiframeからは提供しづらいので、既存の「保存フォルダを開く」導線をそのまま残せばよい

### 6. アプリ内ビューアのUXの定石

「ドキュメントを読ませる」画面としての定石は、規模と用途で変わる:

- **一覧＋プレビューの2ペイン**: メール・ファイルマネージャ的な使い方。一覧から選ぶとすぐ右側に中身が出るため、**複数のレポートを見比べる・素早く行き来する用途に強い**。実装コストは「タブ内に2カラムのレイアウトを作る」程度で、既存の `reports` タブのテーブルをそのまま左側に残し、右側にiframeを追加するだけで実現できる。**今回のようにレポートを何本も生成して比較検討する運用（同じ銘柄で日付違い、複数銘柄を見る等）には最も定石に合う**
- **全画面モーダル**: 一覧から離れて没入して読ませたいときに向く。ただし「戻る」導線（Escキー、閉じるボタン）を自前で用意する必要があり、既存のタブ切り替えUIとは別の操作体系を追加することになる
- **タブ内遷移**（一覧→詳細ビューに画面ごと切り替え、明示的な「戻る」ボタンで一覧に戻る）: モーダルほど大仰でなく、2ペインほど画面が狭くならない。**長文のレポートをじっくり読ませる**という用途には2ペインより向く（横幅を広く使える）

**推奨**: **一覧＋プレビューの2ペイン**を基本とし、一覧の行をクリックすると同じタブ内の右側（または一覧を上、プレビューを下でもよい）にiframeで表示する形。理由:
- 既存の `reports` タブの構造（一覧テーブル＋「開く」ボタン）を大きく壊さずに拡張できる
- レポートは「銘柄×日時」で複数生成されるため、切り替えながら見比べる操作が自然に発生する。2ペインならクリックだけで遷移でき、モーダルのように毎回開閉する手間がない
- 幅は「一覧を細め（銘柄・日時・モデル名程度の列で十分）、プレビューを広く」が定石。レポート本文は `max-width:900px` で組まれているため、プレビュー側の幅がそれ以上あっても本文は中央寄せで問題ない
- キーボード操作は最低限、一覧側に矢印キーでの行移動、Escでプレビューを閉じて一覧へフォーカスを戻す程度を用意すれば十分（既存画面に高度なキーボード操作の仕組みが見当たらないため、過剰実装を避ける）
- 「戻る」操作は2ペインなら本質的に不要（一覧は常に表示されたまま）だが、モバイル的な狭い画面幅を考慮するなら、一覧⇔プレビューをスタック的に切り替えるレスポンシブ対応も将来検討の余地あり（現状のウィンドウ最小幅1100pxを見る限り優先度は低い）

## 判断がつかなかった点（実機で確かめるべきこと）

1. **`iframe.contentWindow.print()` が `sandbox="allow-modals"` のみ（`allow-scripts` 無し）で動くか**は、WebView2の実装依存の可能性がある。動かない場合は印刷は「別ウィンドウ／外部ブラウザで開く」に一本化する
2. **`srcdoc` に数十KB〜のHTML文字列を渡したときの体感速度**（`ExecuteScriptAsync` 経由でPython→JSへ文字列を渡す都合上、非常に大きいレポートだと遅延が出る可能性。今回の実測サイズなら問題ないと推測するが、SVGを何十個も1レポートに詰め込むケースが今後出てくるなら要確認）
3. **SVG内 `<text>` のフォールバックフォント順（`Hiragino Kaku Gothic ProN → Yu Gothic → Meiryo`）が、実際のWindows環境でどのフォントに解決されるか、字形の大きさが `report.html.j2` 本体の文字と揃って見えるか**は目視確認が必要
4. **`prefers-color-scheme` によるダークモード自動追従が、pywebview（Edge WebView2）でOSのテーマ設定を正しく拾うか**（Chromiumベースなので通常は拾うはずだが、pywebviewの起動オプションでテーマが固定されている可能性もゼロではない）
5. **印刷時の背景色・グリッド線の実際の見え方**（「背景のグラフィックを印刷」オプションがWebView2の印刷ダイアログでどう扱われるか）は、実際に印刷プレビューを開かないと確定できない
6. **`webview.create_window(html=...)` を実行中に複数回呼んだ場合のウィンドウ管理**（レポートを連続して何個も別ウィンドウで開いたときのリソース消費、閉じ忘れの扱い）は実装時に軽く負荷確認した方がよい

## まとめ（推奨のみ抜粋）

- **(A) の推奨**: **自前でSVG文字列を組む**（追加依存ゼロ、`xml.sax.saxutils.escape` かJinja2の`autoescape`でエスケープ）。想定サイズは5〜6図入りレポートで**追加7KB程度**（gzip換算で2KB程度）。`pygal`/`svgwrite`はいずれも今の制約下では自前実装に対する優位性が薄く、`matplotlib`/`plotly`(+kaleido)は依存の重さが要件に反するため不採用
- **(B) の推奨**: レポートタブに**一覧＋プレビューの2ペイン**を追加し、新規APIメソッド（`get_report_html(report_id)`、`ai_report.get_report()`のパスから`read_text`するだけ）でHTML文字列を取得して**`iframe.srcdoc` に設定、`sandbox="allow-modals"`（`allow-scripts`・`allow-same-origin`は付けない）で隔離**するのが、Edge WebView2・dev_server双方で確実に動く方法。高さは固定＋内部スクロール。印刷は「別ウィンドウで開く」（`webview.create_window(html=...)`、実行時に新規ウィンドウを追加できることをソースで確認済み）または既存の「外部ブラウザで開く」に委ね、iframeプレビュー自体には印刷ボタンを持たせない設計が安全側
