## 総評

文書の構成・規約への配慮・「需給をAIに送らない」境界の意識は良く、土台コードの読み込みも正確である（土台のテストは本レビューで実行し **252 passed / 15 skipped** を確認した）。

## 指摘事項

### [重大] 1. EDINET の差分管理が「日付単位・登録銘柄でフィルタして破棄」のため、後から登録した銘柄の開示が永久に取れない

- 対象: SPEC §2.4.3、§3 `fetch_log`、DESIGN §1.4
- 問題:
  1. `fetch_log(source='edinet', key=<日付>)` で日付を取得済みにする一方、保存するのは「その時点の登録銘柄に一致した行」だけ。後日あたらしい銘柄を登録しても、過去日付は取得済み扱いなので**その銘柄の過去の開示は二度と取得されない**。銘柄を削除→再登録した場合も同じ（CASCADE で `disclosures` は消えるが `fetch_log` は残る）。
  2. 初回取得範囲が「`registered_at` 以降、または過去1年の**いずれか短い方**」。登録直後は `registered_at` = 今日なので、短い方＝当日のみ。**新規登録銘柄のチャートには開示マーカーが1つも出ない**（株価は `INITIAL_PERIOD="1y"` で1年分ある）。
  3. `fetch_log` の主キーが `(source, key)` で、「`fetch_log` に無い日付のみ取得」と定義されているため、`result='error:…'` の日付も再取得されない。また**当日分**を取得済みにすると、その日の後続提出を取り逃がす。過去分も取下げ・不開示・書類情報修正で更新される（API仕様書 3-1-3-1）。
- 根拠: SPEC の記述どおりに読んだ帰結。過去分の更新は EDINET API 仕様書 p.60「過去分のデータ（全て、既存の情報に対する更新となる）」で確認。https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf
- 提案:
  - `documents.json` の結果は**銘柄で絞る前に**ローカルへ保持する。最も単純なのは日付ごとの生 JSON を `data/edinet_cache/YYYY-MM-DD.json.gz` に保存し、銘柄登録時はキャッシュを再走査して `disclosures` を埋める方式（API 再呼び出し不要）。
  - 取得範囲は「**株価の保有期間（`prices` の最古日）と同じ**、ただし API 上限10年以内」とする。1年分で約365リクエスト（1秒間隔で6〜10分）なので、後述の進捗・中断の仕組み（指摘7）が前提になる。
  - 「確定済み」とみなす条件を `result in ('ok','empty')` かつ `fetched_at` が対象日の翌日 0:30 JST 以降、とする。当日分・エラー分は再取得対象に残す。
  - `test_edinet.py` に「後から登録した銘柄の過去開示が埋まること」を追加する。

### [重大] 2. 銘柄突合が `secCode` のみのため、大量保有・公開買付（＝需給系マーカー）がほぼ全滅し、逆に誤帰属も起きる

- 対象: SPEC §2.4.2、§2.5.3、§3 `disclosures`、DESIGN §2、PLAN P4-2
- 問題: `secCode` は**提出者**の証券コードである。大量保有報告書（350/360）の提出者は多くが非上場のファンド・個人で `secCode` は NULL → SPEC §2.4.2 の「`secCode` が NULL の行はスキップ」で捨てられる。対象会社は `issuerEdinetCode`（大量保有）／`subjectEdinetCode`（公開買付）でしか分からない。
  さらに、登録銘柄 X 社が**他社 Y の株を保有して**大量保有報告書を出した場合、`secCode` 一致で「X 社の需給イベント」として誤表示される。
  DESIGN §2 は「`issuerEdinetCode` で発行会社を引く」と書いているが、SPEC にはその手段（EDINET コード ⇔ 証券コードの対応表）も、`disclosures` の該当カラムも、PLAN のタスクも無い。
- 根拠: EDINET API 仕様書 p.51「提出者証券コード secCode：提出者の証券コードが出力されます」、p.52「issuerEdinetCode：大量保有について発行会社の EDINET コードが出力されます」「subjectEdinetCode：公開買付けについて対象となる EDINET コードが出力されます」（PDF を取得して原文確認済み）。
- 提案:
  - EDINET コードリスト（RESEARCH §1.7 の `Edinetcode.zip`）を取り込み、`stocks.code` → `edinet_code` を解決するタスクを **P4-2 の前に新設**する（テーブル `edinet_codes` か `stocks` への列追加。ZIP 内 CSV の文字コードは実装時に確認）。
  - 突合規則を書類種別で分ける: 350/360 は `issuerEdinetCode`、240〜320 は `subjectEdinetCode`（＋提出者）、それ以外は `edinetCode`（提出者）。`secCode` は補助に格下げ。
  - `disclosures` に `issuer_edinet_code` / `subject_edinet_code` を追加。1書類が複数の登録銘柄に関係し得る（提出者も対象も登録済み）ので、`disclosures(doc_id PK, symbol)` の 1:1 をやめ、`disclosure_links(doc_id, symbol, role)` のような関連テーブルにするか、PK を `(doc_id, symbol)` にする。

### [重大] 3. 日証金 `zandaka.csv` は固定ファイル名・最新日のみ。「未取得日のみ取得」は成立せず、時系列は“ボタンを押した日”しか貯まらない

- 対象: SPEC §2.3、§3 `margin_balances`、§9-1/9-2、DESIGN §1.3、RESEARCH §3.3、PLAN P2-3/P2-4
- 問題: 実ファイルを1回だけ確認した（P2-3 の前倒し）。
  - URL は `https://www.taisyaku.jp/data/zandaka.csv`（**日付なしの固定名**）。ページの説明も「最新データのみ。過去データは銘柄検索機能で抽出」。中身は**1申込日分のみ**。
  - 文字コードは **Shift_JIS 系**（UTF-8 で読むと全面文字化け）、ヘッダ行あり、**約36列**。先頭は `申込日 / 決済日 / 銘柄コード / 銘柄名 / …`、7列目付近に**速報／確報の区分**らしき列、以降は融資（新規・返済・残高）／貸株（新規・返済・残高）／差引残高の株数と金額、回転日数など。
  - つまり RESEARCH §3.3 の「ファイル名に日付が入るため未取得日だけを取れる」は日証金には当てはまらない。SPEC §2.3.2 の `fetch_log key=<日付>` による差分取得は設計として成立しない。
  - 「取得はすべて手動トリガ」（SPEC §1.3）と組み合わさると、**ユーザーが毎営業日ボタンを押さない限り時系列に穴が開く**。穴を階段線で結ぶと「据え置き」に見えてしまい、SPEC が避けようとしている“存在しない値の捏造”になる（日次データの欠測は「据え置き」ではなく「不明」）。
  - 暫定カラムの `loan_balance=貸付（売り）/ borrow_balance=借入（買い）` は用語が実ファイルと合わない。実際は **融資残高（買い方向）／貸株残高（売り方向）**。速報/確報の区別と、日付を申込日・決済日のどちらで持つかも未定義。
- 根拠: https://www.taisyaku.jp/download/ および https://www.taisyaku.jp/data/zandaka.csv を各1回取得して確認。
- 提案（**ユーザー判断が必要**。決定事項1の前提事実が崩れているため蒸し返しには当たらないと判断した）:
  - A案: 蓄積型と割り切る。「取得開始日以降のデータしか無い」ことを UI に明記し、**欠測日は線を切る**（階段でつながない）。取りこぼしを減らすため「アプリ起動時に当日分が未取得なら1回だけ取得」（1日1リクエスト）を許容するかを決める。これは §1.3「常駐ポーリングしない」の例外になる。
  - B案: 過去分を「銘柄検索機能」から取る。ただしこれは別のスクレイピング対象が増えることを意味し、規約・構造・負荷の調査が別途必要（今回は未調査）。
  - C案: 貸借残高ペインを初期リリースから外し、P2-3〜P2-4・P3-3 を後回しにする（指摘「削るべき機能」参照）。
  - いずれの場合も PK は `(symbol, date)` に速報/確報をどう畳むか（確報で上書き、が自然）を SPEC に書く。P2-3 は「P1-5 依存」を外して P0 のスパイクに格上げする。

### [重大] 4. 第三者サイトの実データをテストフィクスチャとして Git にコミットする計画は、SPEC 自身が掲げる「再配布しない」に反する

- 対象: PLAN P2-1（`tests/fixtures/karauri_7203.html`）、P2-3（`zandaka.csv` `meigara.csv`）、SPEC §10 末尾、§7.1
- 問題: `origin` は GitHub（`satsuki19980613/Chronos-Chart`）で、P0-5 で push する計画。karauri.net の HTML 全文や日証金 CSV をフィクスチャとしてコミットすると、**複製して第三者の利用に供する**行為になる。日証金の規約は「複製…方法の如何を問わず第三者の利用に供することを固く禁じます」と明記しており、公開リポジトリなら明確に抵触、非公開でも将来公開した時点で履歴に残る。`.gitignore` は `data/` しか除外していない。
- 根拠: RESEARCH §3.4 に引用済みの日証金規約（本レビューでも同文を確認）。
- 提案: フィクスチャは**構造だけ実物に合わせ、値と名称は架空の合成データ**にする（karauri は `<table id="sort" class="mtb2">` の骨格＋数行、日証金は Shift_JIS・同一ヘッダ＋架空銘柄数行）。実物は `tests/fixtures/real/` に置いて `.gitignore` し、存在するときだけ走る追加テストにする。EDINET の `documents.json` は出典明記で利用可だが、同じ方式に揃えた方が安全。

### [中] 5. `lineType: 2` は階段ではなく**曲線**（Curved）。階段は `1`（`LineType.WithSteps`）

- 対象: RESEARCH §5.3、DESIGN §5.1、SPEC §2.5.2、PLAN P3-2・§4-4（計5箇所）
- 問題: 同梱の `web/vendor/lightweight-charts.standalone.production.js`（v5.2.1）で enum を確認した: `Simple=0, WithSteps=1, Curved=2`。仕様どおり `lineType: 2` と書くと、点と点を**滑らかな曲線で補間**する。「線形補間すると嘘のグラフになる」ことを避けるための指定が、より悪い結果になる。申し送り事項（PLAN §4-4）にも同じ誤記があり、後続セッションが忠実に従うほど誤る。
- 提案: 数値リテラルをやめ `lineType: LWC.LineType.WithSteps` と表記する。全5箇所を修正。

### [中] 6. whitespace data の前提と、階段線の適用範囲の整理

- 対象: SPEC §2.5.2、PLAN P3-1、REVIEW_REQUEST §4.3 の問い
- 問題:
  - 土台の `toSeries()`（`chart.js:99`）は null の点を**単に捨てて**おり、それで時間軸は崩れない（同一チャート内の時間軸は全シリーズの time の和集合で、ローソク足が全営業日を持つため）。需給シリーズに whitespace を入れる必要はなく、P3-1 の「whitespace 用に日足の全日付を含める」は不要。
  - 逆に注意すべきは、**ローソク足に存在しない日付**の需給データ（yfinance 側の欠損日など）を渡すと、時間軸に足の無い列が1本増えること。需給データは `prices` の日付集合でフィルタする（または直前の営業日に寄せる）必要がある。
  - ラインシリーズは whitespace があっても前後の点を結ぶ。したがって「欠測＝線が切れる」にはならない。空売り残高合計（報告が出た日にだけ値が変わる量）は階段が正しいが、**貸借残高は日次データなので階段は不適切**で、欠測は線を切る（シリーズを分割する、または欠測区間の点に透明色を指定する）べき。
  - 設計書は「週次データを日足に重ねる」と書くが、JPX 週次を採用しなかった時点で**週次データは仕様から消えている**。用語が残っているだけなので削除する。
- 提案: §2.5.2 を「空売り残高合計＝WithSteps、最終報告日から最新足までは据え置きで延長」「貸借残高＝通常線、欠測で切る」に書き分ける。

### [中] 7. 長時間処理を「ブロッキング・進捗なし・キャンセル不可」とする設計は、今回の処理時間では成立しない

- 対象: SPEC §4.2 末尾、§2.2.4、REVIEW_REQUEST §4.4 の問い
- 問題: 土台の `update_all` は数秒〜十数秒なのでブロッキングで足りたが、今回は karauri 20銘柄×10秒＝3分超、EDINET 1年分＝6〜10分。SPEC は「進捗を表示」と書くが、ブロッキング API には進捗を返す経路が無い。「キャンセル不可」は相手サーバーへの配慮としても逆効果（間違えて実行しても止められない）。
- 提案: pywebview は API 呼び出しごとに別スレッドで動く（`database.py` 冒頭コメントのとおり）ので、`start_job()` → `job_status(job_id)` をポーリング → `cancel_job(job_id)` のジョブ方式にする。待機は `time.sleep` ではなく `threading.Event.wait(interval)` にすれば中断は数行で実現できる。あわせて次を SPEC に明記する:
  - `Database.write()` は接続を開いている間 `_write_lock` を保持する。**HTTP 待ちの間はロックを持たない**（取得→パース→短いトランザクションで保存、を銘柄/日付ごとに）。
  - `_response` デコレータがユーザー向けメッセージとして扱うのは `FetchError` / `ValueError` のみ。新設する例外（設定不備・クォータ不足・サイト構造変更）をどちらに寄せるか決める。

### [中] 8. Gemini 429 は RPM 超過と RPD 超過を区別できる。「区別できない」前提の“1日打ち切り”は不要に厳しい

- 対象: RESEARCH §4.3、SPEC §2.7.2、§6、REVIEW_REQUEST §4.5 の問い
- 問題: RESEARCH §6-2 で「429 レスポンスボディの正確なフィールド構造」を**未確認**としながら、§4.3 と SPEC は「区別するフィールドは無い」と**断定**している。実際の 429 には `google.rpc.QuotaFailure` が含まれ、`violations[].quotaId` が `GenerateRequestsPerDayPerProjectPerModel-FreeTier` / `…PerMinute…` のように日次・分次を示し、`google.rpc.RetryInfo.retryDelay` も付く。
- 根拠: https://discuss.ai.google.dev/t/429-resource-exhausted/111737 ほか多数の報告。公式に安定仕様として保証された形式ではない点に注意。
- 提案: `ClientError` の詳細から `quotaId` を読み、`PerDay` を含む→その日を打ち切り、`PerMinute` を含む→`retryDelay` だけ待って1回だけ再送、判別不能→安全側で打ち切り。加えて、誤判定や自前カウンタのずれに備え、**打ち切りフラグを手動解除するボタン**を設定タブに置く。
  なお公式ページには「Rate limits are applied per project, not per API key」とあり、同じプロジェクトを AI Studio など他で使うと自前カウンタは実態とずれる。「自前カウンタを正とする」ではなく「自前カウンタは下限の見積り」と位置づける。

### [中] 9. `google-genai` は既定では自動リトライしない。「SDK が最大4回リトライする」は誤り

- 対象: RESEARCH §4.3、SPEC §2.7.2 末尾、PLAN P6-1
- 問題: SDK ソースの `retry_args()` は `options is None` のとき `stop_after_attempt(1)`（＝再試行なし）を返す。RESEARCH が挙げた「5回・初回1秒・最大60秒・408/429/5xx」は `HttpRetryOptions` を**明示的に渡したとき**の既定値である。SPEC の「SDK が自動リトライするのでアプリ側で二重にしない」に従うと、**どこもリトライしない**実装になる。逆に誰かが `retry_options` を有効にすると、429 のたびに SDK が黙って最大5回送信し、自前カウンタは1回しか数えないので RPD 管理が壊れる。
- 根拠: https://raw.githubusercontent.com/googleapis/python-genai/main/google/genai/_api_client.py
- 提案: 「SDK の `retry_options` は**設定しない**。再送はアプリ側で行い、**送信を試みるたびに** `ai_usage.requests` を加算する（成功時ではなく送信前に加算。失敗したリクエストも枠を消費するため）」と SPEC に明記する。

### [中] 10. スキーマのフィールド順は「根拠 → 結論」にすべき。表示順はテンプレート側で決められる

- 対象: RESEARCH §4.4、DESIGN §4.2、SPEC §2.7.4、REVIEW_REQUEST §4.5 の問い
- 問題: 懸念のとおり。自己回帰生成では先に出力した `verdict` / `confidence` が後続の `technical.evidence` を条件づけるため、**根拠が結論の後付け**になる。RESEARCH の「結論→根拠の順に定義すると質が上がる」には出典が無く、一般的な知見とは逆。thinking を「低め設定から始める」（RESEARCH §4.4）方針ではこの影響がさらに強く出る。
- 提案: 定義順を `technical → disclosure → risks → watch_points → verdict → confidence → summary` にする。HTML は Jinja2 で組むので、**レポート上の表示順は結論を先頭にしたままにできる**（この設計の利点がそのまま活きる）。併せて `confidence: int (0-100)` は LLM の自己申告で較正されていないため、`Literal["low","medium","high"]` に落とすか削除を勧める。

### [中] 11. `MAX_TOKENS` 時に「期間を縮めて再実行」を促すのは原因と対策が合っていない

- 対象: SPEC §2.7.5-1、§6、REVIEW_REQUEST §4.5 の問い
- 問題: `MAX_TOKENS` は**出力**側の上限。入力期間（20/60/120日）を縮めても出力量はほぼ変わらない。このスキーマの出力は1〜2千トークン程度で、8192 に達する主因は **thinking トークンが出力枠を消費する**ことか、リストの際限ない列挙である。自動の分割生成は過剰。
- 提案: (1) thinking 予算を設定項目にして既定を小さく固定、(2) スキーマの `list[str]` に件数上限（`max_length`）と各要素の文字数目安を指定、(3) `MAX_TOKENS` 時は「出力トークン上限を上げる／thinking を下げる」を案内、の3点。ユーザーへの丸投げでも自動分割でもなく、原因を潰す。
  また再依頼の事前見積りは「RPD 残りが3以上ないと実行不可」という挙動になり、1日の最後の2回が使えなくなる。事前条件は「残り1以上」とし、**再依頼のたびに直前でガードを再評価**する方が素直。

### [中] 12. `event_date` を DB に持たず、表示時に株価の日付列から決める（祝日カレンダー問題の解消）

- 対象: SPEC §3 `disclosures.event_date`、§2.5.3、REVIEW_REQUEST §4.2 の問い
- 問題: 「直後の営業日」を取得時に確定して保存するには祝日カレンダーが要る（土台の `_future_cloud` は祝日非考慮と明記）。また取得時点で未来の営業日の株価はまだ無く、保存した値が正しい保証が無い。臨時休場や yfinance の欠損日にも追従できない。
- 提案: DB には `submit_at` だけを持ち、`events.py` が payload 生成時に `prices.date` の昇順リストへ二分探索して「提出日以降で最初に足が存在する日」を求める。該当する足がまだ無い開示はマーカーを出さず、イベント欄にだけ出す。**祝日ライブラリも祝日表も不要**になり、`idx_disclosures_symbol_date` は `submit_at` に張り替える。
  補足: EDINET の提出は引け後（15:30 以降）が多い。提出日の足に付けたマーカーは「その日の値動きの原因」には見えないよう、イベント欄に提出**時刻**も出すことを勧める。

### [中] 13. 「決算系」マーカーの実態は“決算発表”ではない。四半期報告書は廃止済み

- 対象: SPEC §2.5.3、§1.3、RESEARCH §1.4/§1.5、DESIGN §2
- 問題: 金商法改正により **2024年4月1日以後に開始する四半期から四半期報告書（140/150）は廃止**され、半期報告書に一本化された。RESEARCH はこれに触れていない。今後 EDINET で得られる「決算系」は有報と半期報の年2回で、しかも提出は決算短信（TDnet）の数週間〜3か月後。株価が反応する決算発表日とは一致しない。これを青丸で「決算」と表示すると、ツールの目的（値動きと開示の突き合わせ）に対して誤解を生む。決定事項3（EDINET のみ）を蒸し返すものではなく、**表示名と期待値の問題**である。
- 根拠: 金融庁の改正（2023-11-29 公布・2024-04-01 施行）。解説: https://kpmg.com/jp/ja/insights/2024/05/accounting-ppa.html
- 提案: 分類名を「有報・半期報」に改め、マーカー文言も「有報」「半期」とする。画面とレポートの免責に「決算短信・業績修正は対象外で、決算発表日は表示されない」を明記。AI プロンプトにも同じ前提を1行入れる（開示一覧が空でも“材料なし”と誤読させない）。140/150 は過去分の表示用として残す。

### [中] 14. `short_positions` は報告者“名”ではなく報告者 ID をキーにし、保存は銘柄単位の全置換にする

- 対象: SPEC §2.2.2、§2.2.3、§3、REVIEW_REQUEST §4.2 の問い
- 問題と確認結果:
  - 実ページ（7203 を1回取得）では、同一報告者・同一計算日の重複行は見当たらなかった。ただし1銘柄・約40行の観察であり「無い」とは言い切れない。
  - より現実的なリスクは**名称ゆれ**。機関名は `<a href="/<code>/?f=<機関ID>">` でリンクされており（RESEARCH §3.2）、サイト側は ID で同一性を管理している。名称が変わると `holder` 文字列キーでは別人扱いになり、§2.2.3 の「報告者ごとの最新1件」で**二重計上**される。
  - ページには全履歴が1枚で載るので、行単位の upsert より「パース成功時にその銘柄の行を1トランザクションで全置換」の方が単純で、サイト側の訂正・削除にも追従する。
  - 「報告義務消失」を `note` の文字列一致だけで判定するのは脆い。
- 提案: `holder_id`（リンクの `f=` の値）を保存し PK を `(symbol, calc_date, holder_id)` に。万一の重複は後勝ち＋警告ログ（全体を失敗させない）。消失判定は「`note` に“消失”を含む **または** `ratio < 0.5`」の二重条件にし、未知の `note` 文言はログに出す。
  ペインのラベルは「空売り残高（報告義務 0.5% 以上の合計・本ツール算出）」とし、**0 は“空売りが無い”ではなく“0.5% 以上の報告者がいない”**意味だと注記する（7203 は最新行が 2022-04 で、大型株ではペインがほぼ空になる）。

### [中] 15. `disclosure_facts` のホワイトリストは「要素ID」だけでは足りない（会計基準とコンテキスト）

- 対象: SPEC §2.4.6、§9-7、PLAN P4-4
- 問題: 売上高ひとつ取っても、日本基準・IFRS・米国基準で要素 ID が異なり、同じ要素が「当期／前期／5期分の経営指標」「連結／個別」の複数コンテキストで出る。要素 ID だけで絞ると、IFRS 採用企業（大型株に多い）で売上高が**静かに欠落**する。「直近値」を AI に渡す（§2.7.3）には、コンテキスト ID の選択規則も要る。
- 提案: まず「主要な経営指標等の推移」（`…SummaryOfBusinessResults` 系）に限定し、`相対年度=当期` かつ `連結優先・無ければ個別` を規則として SPEC に書く。P4-4 の完了条件に「日本基準と IFRS の2社でフィクスチャ（合成）を用意」を加える。PK 衝突は `INSERT OR REPLACE`＋警告で吸収し、書類全体を失敗させない。
  そもそも `disclosure_facts` の利用先は AI プロンプトの「財務数値」だけで、画面仕様に表示箇所が無い（`get_disclosure` は定義されているが UI タスクが無い）。後述のとおり**削減候補**。

### [中] 16. API キーを平文で置く `data/` が OneDrive 同期フォルダ配下にある

- 対象: SPEC §7.3、§2.1.2
- 問題: SPEC は「OS のユーザーアカウントで保護されることを前提」とするが、現在の作業ディレクトリは `C:\Users\…\OneDrive\ドキュメント\…` で、既定の `DATA_DIR = BASE_DIR / "data"` は**クラウドに同期される**。EDINET / Gemini のキーが平文で Microsoft のクラウドに上がる。加えて SQLite の WAL（`-wal` `-shm`）を同期ツールが掴むと、ロック競合や破損の既知の原因になる。
- 提案: キーは `keyring`（Windows 資格情報マネージャー）に保存し、DB にはキー以外の設定だけを置く。少なくとも、既定の保存先を `%LOCALAPPDATA%\ChronosChart` に変えるか、同期フォルダ配下を検出したら設定タブに警告を出す。

### [軽微] 17. マーカーに関する2つの事実誤認（設計判断は概ね維持でよい）

- 対象: RESEARCH §5.4、SPEC §2.5.3/§2.6、PLAN P5-2/P5-4・§4-3
- 確認結果（同梱 v5.2.1 のソースで確認）:
  - `createSeriesMarkers()` は呼ぶたびに新しいプリミティブを `attachPrimitive` する。**複数回呼んでも上書きされず、両方描画される**。「後勝ちで消える」は誤り。ただし別プラグイン同士は同じ足・同じ位置での重なり回避をしないので、**1配列にマージする方針自体は妥当**。理由の記述だけ直す。
  - マーカーのヒットテストは存在する。マーカーに `id` を付けると、`subscribeClick` / `subscribeCrosshairMove` の `param.hoveredObjectId` にその `id` が入る。「ヒットテスト API は無い」は誤り。`param.time` 方式でも動くが、`hoveredObjectId` の方が正確で実装も短い。
- 追加の注意: 土台ではマーカーが `overlays.has("signals")` の中で作られている。マージするなら、**シグナルのチップが OFF でも開示マーカーは出る**よう配列構築を分岐の外に出し、開示側にも独立したチップを用意する。マージ後の配列は time 昇順にソートする。

### [軽微] 18. スクレイピング作法の細部

- 対象: SPEC §2.2.4、§4.1
- 判断: 10秒・直列・識別可能 UA は個人利用として十分に控えめ。robots.txt は本レビューでも取得し、RESEARCH §3.2 の記載と一致した。SPEC §7.1 は「許可」とは解釈しておらず「対象外だが作法を守る」という書き方で、問題ない。`scrape_contact` 必須も妥当（ただし**個人のメールアドレスが第三者サイトへ毎回送られる**ことを設定画面に明記する）。

  - §4.1 の共通リトライ（1s→2s→4s）は karauri の最小間隔10秒を下回る。**バックオフはソースの最小間隔を下限**にする。

### [提案] 22. 需給を送らないことの担保を、テストの作り方で強くする

- 「プロンプト文字列に需給データが含まれないこと」は、数値が偶然一致し得るので素朴には検証できない。**番兵値方式**にする: テスト DB の需給3テーブルに `SENTINEL_HOLDER_9f3a` や `98.7654321` のような現実にあり得ない値を入れ、生成プロンプト・再依頼プロンプト・レポート HTML のいずれにも現れないことを確認する。
- 構造面: `prompt.py` は DB を直接触らず、許可された getter だけを持つ読み取り用ファサードから組み立てた凍結 dataclass を受け取る。`app/ai/` 配下のソースに `short_` `margin_` `taisyaku` `karauri` が出現しないことを AST/文字列で検査するテストを足す。
- 抜け道になり得る経路を SPEC に名指しで禁止する: (a) `service.dashboard()` の payload（今後 `chart.short` を含む）をプロンプト材料に流用しない、(b) `ai_export.py` を拡張する際に需給を足さない、(c) RESEARCH §5.7 の `takeScreenshot()` によるチャート画像（需給ペインが写る）をレポートや送信に使わない。

### [提案] 23. 削るべき機能（1人で完遂するために）

優先度の低い順に切れるもの:

1. **`disclosure_facts` / XBRL CSV パース（P4-4）を初期リリースから外す。** 利用先が AI プロンプトの財務数値だけで画面に表示箇所が無く、UTF-16LE・会計基準差・コンテキスト選択・DB サイズと、P4 の難所が集中している。P6 完了後の追加機能にすれば、分類 A/B の区別も当面不要になる。
2. **PDF のローカル保存**（`disclosure_fetch_pdf`・`fetch_disclosure_body`・`open_disclosure`・`data/disclosures/` の管理・銘柄削除時のディレクトリ掃除）。イベント欄から EDINET の書類閲覧ページを既定ブラウザで開くだけにすれば丸ごと不要になる（URL 形式は実装時に要確認）。
3. 貸借残高ペイン（指摘3のC案）。
4. 空売りペインの副線 `holders`、期間選択の3段階、`confidence`。

1と2を外すと P4 は6タスク→3タスク程度になり、全体の2割前後が減る。

### [提案] 24. イベント欄の配置

チャートのコンテナ高は `400 + ペイン数×125px`（`chart.js:128`）で、ペインを増やすほど縦に伸びる（10ペイン選択で約1,650px、需給2つを足すと1,900px）。窮屈にはならずチップ UI も `PANES` から汎用生成されるので破綻しないが、**「チャート直下」のイベント欄はローソク足から大きく離れ**、行クリック→スクロールの連動が画面外で起きる。イベント欄はチャートの上、または右側のサイドパネルに置く方が連動の意味が出る。なおチップ切替のたびにチャートは破棄・再生成されるため、表示範囲の購読は `render()` の戻り値 API 経由で張り直す設計にしておく。
